# conversation_archiving.md — архивация публичных бесед агентов

## WHEN

- Смена серии агента (0A -> 1A -> 2A, 0B -> 1B -> 2B, и т.д.).
- Явное указание оператора: «выгрузи беседу X в RAG».
- Плановая ревизия архива (раз в крупную веху — MILESTONE).

## WHO

- B (помощник) — исполнитель выгрузки, ведёт logs/B/conversations/.
- A (ведущий) — инициатор, даёт добро на выгрузку и место в RAG.
- C (апрувер) — проверяет, что беседа попала в индекс и связана с RAG.
- Оператор — источник share-ссылок и верховный судья.

## STEPS

### 1. Получить share-URL
Оператор даёт публичную share-ссылку на беседу. Формат:
`https://chat.deepseek.com/share/<token>`.
Если ссылки нет — задача не выполнима, ждать.

### 2. Выгрузить
Инструмент: `sandbox/export_share.py`.

    python sandbox/export_share.py --url <share-url> \
      --out logs/B/conversations/<series>_share.md \
      --port 9223 --wait 12

Требования: Chrome-B запущен, залогинен в чат LLM (для WAF).

### 3. Контроль качества (ОБЯЗАТЕЛЬНО)
Прочитать первые строки через op=read. Проверить:
- `final_url` == `source` (нет редиректа);
- тело начинается с «Shared Conversation»;
- в теле есть реальные реплики, не только UI;
- НЕТ собственных id текущей сессии (`next_id:`, `[ALIVE?]`,
  id активного префикса).

Признак провала — выгружен личный чат пользователя, а не публичная
копия. Файл удалить, метод пересмотреть.

### 3a. Переходные серии (допустимое отклонение)

Если в теле share-страницы встречается более одной серии id —
это **не автоматический провал QC**. Возможные причины:

- **Передача сессии.** Ведущий 4A в своём чате обсуждал будущего
  преемника 5A, планировал его диапазон, писал примеры команд
  с id AAAA6xxx. Эти id — не исполненные команды 4A, а
  проектная работа над следующей серией.
- **Продолжение в том же чате.** 5A начал работу в чате 4A,
  не создавая новый. Тогда в одном треде законно есть хвост
  4A (AAAA5xxx) и начало 5A (AAAA6xxx).

Правило:
1. Проверить — открывается ли тело репликой старой серии
   (4A) и заканчивается ли репликами новой (5A).
2. Проверить, что id новой серии — это **планы или первые
   шаги**, а не полный рабочий лог 5A.
3. Если так — файл валиден, сохранить с пометкой в шапке:
   - `series: 4A (переходная, включает первые шаги 5A)`
   - `id_range: AAAA5xxx (4A) + AAAA6xxx (5A, вступление)`
   - `note: смешанный тред, апрув A по правилу 3a.`
4. Если смесь не объясняется передачей — FAIL.

### 4. Индексация в RAG
- Добавить файл в `logs/B/conversations/README.md` (таблица).
- Если беседа меняет картину проекта — короткая запись в
  `MILESTONE.md` со ссылкой на файл.
- Тяжёлые беседы (много КБ) в INDEX.md не вносить — там только
  процедура и README. Индексируется процедура, не каждый файл.

### 5. Запись в дневник
В `logs/B/YYYY-MM.md` — одна строка: серия, байты, статус выгрузки.

## Формат хранения

    logs/B/conversations/
      0A_share.md
      1A_share.md
      0B_share.md
      1B_share.md     (когда появится)
      README.md       (описание, таблица, метод)

## Правило смены серии (3C / 2C)

При вступлении новой серии (например, 3C вместо 2C):
1. Новый агент запрашивает у оператора лог прошлой сессии.
2. Читает его (share-URL -> logs/B/conversations/ или полный лог
   logs/council_chat/).
3. Знакомится с функциями, хвостами, открытыми вопросами.
4. Только после этого приступает к работе.
Цель: не терять контекст при смене поколений.

## Что НЕ делать

- Не выгружать личные чаты без явного share-URL от оператора
  (приватность).
- Не перезаписывать существующий файл без бэкапа/проверки.
- Не выгружать share-страницы из залогиненного контекста напрямую
  в основной чат (метод new_page обязателен).
- Не плодить копии: один файл на серию.
